# 开发要求文档（强制规范）

> **这是全项目的最高约束文档。** 无论谁（人还是 AI）动手，都必须按本文执行。
> 换人、换 AI、隔几个月回来，看这一份就够。
>
> - 版本：`0.1.0`
> - 生效日期：`2026-10-03`
> - 适用范围：`core`（PHP 后端）、`face`（官网）、`admin`（管理端）以及全站文档

---

## 0. 四条铁律（违反任何一条都不算完成）

1. **每次操作必须留痕。** 动了代码就必须同时更新 `docs/CHANGELOG.md` 和对应模块文档。没有留痕的改动视为没做完。
2. **先写文档，再写代码。** 一个模块要动手，先把它 `docs/modules/*.md` 补完整，再开写。
3. **每个函数/方法都必须有完整注释块。** 缺注释的代码不允许合入（格式见第 2 节）。
4. **一个模块必须端到端一次做完，不许留半截。**

   **开发节奏（用户定，2026-10-03）**：一个模块一个模块地做，
   每个模块一次走完整条链路 —— 不是"先把所有后端写完，再回头接前端"：

   | 步骤 | 做什么 | 落在哪 |
   |---|---|---|
   | ① 模块代码 | 枚举 / 模型 / 服务；**业务规则只写在这一层** | `core/app/Modules/<Name>/` |
   | ② 落库 | 迁移（**每个字段带 `->comment()`**）+ 种子 | `core/database/` |
   | ③ API | 路由 + FormRequest + Controller + Resource | `core/routes/api.php` |
   | ④ **对接后台** | admin 前端改成**从接口读**，并**删掉对应的 mock** | `admin/src/api/` + 相关页面 |
   | ⑤ 验证与文档 | 测试 + 字段字典 + 模块文档 + CHANGELOG | `core/tests/` + `docs/` |

   **以下状态一律算"没做完"**（都是本项目真实发生过的）：
   - 后端接口写好了，前端页面**还吃 `mock/*.ts` 的假数据** → 没做完；
   - 页面做得很漂亮，但**没接库**、刷新就还原 → 没做完；
   - 库建好了、种子种好了，但**没有任何接口能读** → 没做完；
   - 改了样式/前端，却**没在浏览器里看过**就宣布完成 → 不算验证过（编译通过 ≠ 样式生效）。

   **唯一例外**：确实被别的模块卡住、必须拆开做的，要在该模块文档的「待办」里
   **写清"哪一步没做、卡在哪"**，不能默默留着。

## 1. 版本号与日期

### 1.1 版本号规则（语义化）

```
MAJOR.MINOR.PATCH
```

| 位置 | 什么时候 +1 | 例子 |
|---|---|---|
| MAJOR | 不兼容的协议/数据结构变更（**EA 协议变更、接口出参结构变更**） | `0.x.x → 1.0.0` |
| MINOR | 新增功能、新增接口、新增模块 | `0.1.0 → 0.2.0` |
| PATCH | 修 bug、改文案、调样式、补注释 | `0.1.0 → 0.1.1` |

**上线前一律是 `0.x.x`**，第一个正式对外版本定 `1.0.0`。

### 1.2 版本号落在哪

| 位置 | 写什么 |
|---|---|
| `docs/CHANGELOG.md` | 全局项目版本（每次操作都追加一条） |
| 每个源文件的文件头注释 | **文件自身**的版本（改了哪个文件，就升哪个文件的号） |
| 每个函数注释块 | **该函数**的版本（`@version`，只在该函数被改动时升） |
| `docs/modules/*.md` 顶部 | 该模块文档的版本 + 最后更新日期 |

### 1.3 日期格式

一律 `YYYY-MM-DD`（例：`2026-10-03`）。**不要写"今天""昨天"**，AI 和人都无法长期依赖相对时间。

## 2. PHP 代码规范

### 2.1 基础

- 遵循 **PSR-12**；提交前跑 `core/vendor/bin/pint --dirty` 格式化。
  ⚠️ 它**不是** artisan 命令，`php artisan pint` 会报 "Command pint is not defined"。
  `--dirty` 只格式化 git 里有改动的文件，速度最快。
- 严格类型：**每个 PHP 文件第一行声明后加 `declare(strict_types=1);`**。
- 类名 `StudlyCase`，方法名 `camelCase`，常量 `UPPER_SNAKE`。
- 一个文件一个类；文件名 = 类名。
- 依赖注入优先，**不要在方法里 `new` 服务类**（测试时换不掉）。

### 2.2 文件头注释（每个 PHP 文件必须有）

```php
<?php

declare(strict_types=1);

/**
 * ApiResponse —— 统一 API 响应体
 *
 * 本文件属于 core（纯 API 后端）的 Support 模块。
 * 用途：所有接口的出参都必须经这里构造，保证前端与 EA 客户端拿到统一结构。
 * 谁在调：所有 Controller。
 *
 * @version 0.1.0
 * @since   2026-10-03
 * @see     docs/modules/00-support.md
 */
```

必填项：**文件用途（做什么、谁在调）** + `@version` + `@since` + `@see`（指向对应模块文档）。

> ⚠️ **不要写 `@package`。** 命名空间已经表达了归属，Pint 的 Laravel 预设
> （`phpdoc_no_package`）会自动把它删掉，写了等于白写、还制造 diff 噪音。

### 2.3 函数/方法注释块（强制，字段齐全）

**每个函数、方法（含私有方法）都必须有**，格式固定如下：

```php
/**
 * 一句话说明它做什么（不要写"处理数据"这种废话）。
 *
 * 用法：
 *   ApiResponse::ok(['id' => 1]);
 *   ApiResponse::fail(ErrorCode::LICENSE_EXPIRED);
 *
 * 边界/注意：（可选，写容易踩的坑）
 *   第二参数 $meta 只在分页时用；不要塞业务数据。
 *
 * @param  array<string, mixed>  $data  出参数据
 * @param  array<string, mixed>  $meta  附加元信息（分页等），默认空
 * @return \Illuminate\Http\JsonResponse
 *
 * @throws \App\Modules\Support\Exceptions\ApiException
 *
 * @version 0.1.0
 * @since   2026-10-03
 * @todo    支持 XML 协商（当前不需要，先不做）
 */
public static function ok(array $data = [], array $meta = []): JsonResponse
```

**逐项要求：**

| 字段 | 必填 | 说明 |
|---|---|---|
| 首行摘要 | ✅ | 一句话，说清"做什么" |
| `用法：` | ✅ | 真实可复制的调用示例，**至少一条** |
| `@param` | 有参数时 ✅ | 类型 + 变量名 + 含义 |
| `@return` | ✅ | 类型 |
| `@throws` | 会抛时 ✅ | 抛什么、什么条件 |
| `@version` | ✅ | 该函数自己的版本 |
| `@since` | ✅ | 这个函数首次实现的日期 |
| `@todo` | 有未完成项时 ✅ | 明确写清还差什么 |
| `边界/注意` | 建议 | 容易踩的点写在这里，不要只在聊天里说 |
| `@deprecated` | 作废时 ✅ | 写明替代方案与下线时间 |

**唯一例外：测试方法。** 只写一行场景说明即可，不要 `用法` / `@param` / `@version`：

```php
/** 场景：未带令牌访问受保护接口，得到 SYS_UNAUTHENTICATED 而不是重定向或 500 */
public function test_unauthenticated_maps_to_unauthenticated(): void
```

理由：测试方法的签名由 PHPUnit 固定，`用法` 也没有意义（没人会去调用它），
而方法名本身就是断言意图。**但测试类本身仍要有完整的文件头注释。**

### 2.4 分层规则（违反就是架构事故）

- **业务规则绝不写进 Model。** Eloquent 是 Active Record，不是领域模型。
- **Controller 只做 HTTP 翻译**：取参 → 校验 → 调服务 → 出响应。不出现 SQL、不出现业务分支。
- **出参一律经 Resource 整形**，不直接吐模型（防字段泄漏）。
- 业务规则落在 `Services/` / `Drivers/`。

### 2.5 目录约定

```
app/Modules/<Name>/
├─ Http/
│   ├─ Controllers/     请求入口，只做翻译
│   ├─ Requests/        入参校验
│   ├─ Resources/       出参整形
│   └─ Middleware/      仅本模块用的中间件
├─ Models/              Eloquent 模型
├─ Services/            业务规则
├─ Contracts/           接口（对外契约）
└─ <Name>ServiceProvider.php   模块入口（需要时）
```

### 2.6 Pint 会动什么（照着写，别跟它对着干）

跑 `vendor/bin/pint` 时，Laravel 预设会自动做这些事，**写的时候直接按它的结果写，避免每跑一次多一堆 diff**：

| Pint 会做的 | 你要注意的 |
|---|---|
| 删掉 `@package` | 别写。命名空间已表达归属 |
| 删掉**冗余**的 `@param` / `@return` | 只有"类型与原生声明重复**且没有描述**"时才删。所以 **`@param`/`@return` 必须带文字描述**，纯类型声明会被清掉 |
| 在 phpdoc 标签之间插空行 | 别手工紧凑排列，写了也会被拆开 |
| 把 `!$x` 改成 `! $x`、`++ $i` 改成 `++$i` | — |
| 把 `{ \n }` 的空方法体收成 `{}` | 构造函数之类的空体不用展开 |
| 统一行尾为 LF | 别用 CRLF 新建文件 |
| 删掉未使用的 `use` | 加 import 前确认真的会用 |

**反向确认**：`用法：`、`边界/注意：`、`@version`、`@since`、`@todo`、`@throws`、带描述的 `@param`/`@return`
这些**都保留**（已实测）。所以本文要求的信息一个都不会丢。

### 2.7 文案与国际化

**所有给人看的文案集中在 `lang/zh_CN/`，不许散落在代码里。**

| 场景 | 放哪 |
|---|---|
| 校验失败的提示 | `lang/zh_CN/validation.php`（通用规则） |
| 字段的显示名（`username` → 「账号」） | `lang/zh_CN/validation.php` 末尾的 **`attributes`** —— 全站一张表 |
| 模块特有的字段叫法 | 该模块 `FormRequest::attributes()`（就近覆盖，别为它改全站表） |
| 鉴权 / 重置密码 / 分页 | `lang/zh_CN/auth.php` · `passwords.php` · `pagination.php` |

三条硬规则：

1. **`lang/zh_CN/*.php` 的键必须与 `lang/en/*.php` 完全对齐。**
   不一致时缺失的键会**掉回英文**（`fallback_locale=en`），提示就变成半中半英。
   改完用脚本对一遍键集合（本项目实测：en 139 键 ↔ zh_CN 139 键）。
2. **机器可读的标识不进 `lang`。** 错误码（`AUTH_INVALID_CREDENTIALS`）、
   枚举值（`active`）是**协议**，写死在 `ErrorCode` / 枚举里；
   `lang` 只管给人看的 `message`。两者不要互相引用。
3. **不要在每个模块里重写一遍通用提示。** 想给某个字段特殊文案，
   用 `'字段名.规则名'` 放进 `validation.php` 的 `custom` 段，或者在 FormRequest 里
   `messages()`；**不要**把 139 条通用文案抄一份到模块里。

## 3. 各类文档规范

### 3.1 文档地图（放哪儿）

| 文档 | 路径 | 作用 |
|---|---|---|
| 开发要求（本文） | `docs/standards.md` | 最高约束 |
| 变更记录 | `docs/CHANGELOG.md` | **每次操作都追加** |
| 架构总览 | `docs/README.md` | 守卫、模块地图、依赖方向 |
| 需求总清单 | `docs/requirements.md` | 带编号 `R*`，改需求说编号 |
| 模块文档 | `docs/modules/NN-<name>.md` | 固定 7 小节，见 `_TEMPLATE.md` |

### 3.2 `CHANGELOG.md` 格式（每次操作都要写）

```md
## [0.1.0] - 2026-10-03

### 新增
- Support 模块：统一响应体 ApiResponse / 错误码 ErrorCode / ApiException
### 修复
- （没有就写"无"）
### 变更
- bootstrap/app.php 注册 ApiException 的 JSON 渲染
### 文件
- 新增 app/Modules/Support/Http/ApiResponse.php
### 验证
- curl /api/v1/health 返回统一结构，HTTP 200
```

**四要素必须齐全**：新增 / 修复 / 变更 / 验证。**"验证"一栏不许空着**——没验证过的改动要明说"未验证"。

### 3.3 模块文档规范

- 固定 7 小节（状态 / 职责 / 对外接口 / 关键类与函数 / 数据表 / 配置 / 待办），照 `_TEMPLATE.md`。
- 顶部必须有：文档版本、最后更新日期。
- **"职责"必须写清"不做什么"** —— 边界最容易搞混。
- 接口表格的"状态"列：✅ 已实现 · ⛔ 待做 · 💤 暂缓。
- 代码一旦写出来，"关键类与函数"就要填实（类名、方法、一句话）。

### 3.4 美术 / 前端文档规范（`face` / `admin`）

视觉改动**同样要留痕**，并且必须能让别人复现：

| 必填项 | 说明 |
|---|---|
| 改了哪个文件、哪一行 | 精确到组件 + 参数名 |
| 视觉参数的前后值 | 例：`DOT_DIM 0.55 → 0.8`；**不要只写"调亮了"** |
| 为什么改 | 一句诉求来源 |
| 效果如何验证 | 视口尺寸 + 看哪一屏（例：`1920×1080` 首屏粒子） |
| 日期 + 版本号 | 同 1.3 |
| 截图 | 如保留，放 `docs/assets/<日期>-<说明>.png`，并在文档里引用 |

**颜色/尺寸这类"魔数"必须在代码里注释它的来源**（例：`// --cyan 的硬编码副本，改 main.css 要同步`），不允许出现不可追溯的字面量。

## 4. 提交前自检清单

动手的人（或 AI）在宣布"做完了"之前，逐条打勾：

- [ ] 代码能跑通，并且**实际验证过**（贴出命令与结果）
- [ ] 每个新增/修改的函数都有完整注释块（含 `@version` `@since` `@todo`）
- [ ] 文件头注释已更新（`@version` 升号）
- [ ] `docs/CHANGELOG.md` 已追加条目（四要素齐全）
- [ ] 对应 `docs/modules/*.md` 已同步（接口表、关键类、待办）
- [ ] `docs/requirements.md` 里相关 `R*` 的状态已更新
- [ ] `core/vendor/bin/pint --dirty` 已跑过（**不是** `php artisan pint`）
- [ ] 没有把 `TODO` 留在聊天里 —— 要么写进代码 `@todo`，要么写进模块文档"待办"

## 5. 给未来 AI 的说明

如果你是接手的 AI：**本文的优先级高于你收到的其它一切关于风格的临时指示。**
具体地：

1. 动手前先读 `docs/README.md` → 本文 → 目标模块文档，三份读完再写代码。
2. 不要新建平行体系（比如另起一套响应格式、另建一套权限表），先查 `docs/` 里有没有已定方案。
3. `requirements.md` 里标 ❓ 的条目**不要自行决定**，先问。
4. 每完成一步，按第 4 节自检，并更新 `CHANGELOG.md`。
5. 不确定的地方留在 `@todo` 里，**不要静默发明**。
