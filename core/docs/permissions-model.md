# 权限落地模型与推进计划

> 文档版本：`1.0.0` · 最后更新：`2026-10-03`
> 配套：`docs/permissions.md`（**权限点总表，由命令从数据库生成**）

## 0. 先认清现状（别误会）

| 能力 | 现状 |
|---|---|
| 权限点能管（增删改） | ✅ 后台「权限点管理」 |
| 角色能配（基线 + 个人增减） | ✅ 后台「身份权限」 |
| 数据落库、接口可读 | ✅ 14 组 / 121 个 / 5 个角色 |
| **接口真的按权限拦** | ❌ **还没做** |

**所以现在改权限不影响任何接口行为。** 本文就是要把最后那一格里的事规划清楚。

---

## 1. 理论模型（先把三个概念拆开，混在一起必出错）

### 1.1 三种"能不能"，不是一回事

| 概念 | 回答的问题 | 用什么表达 | 例子 |
|---|---|---|---|
| **认证** | 你是谁？ | 四层守卫 `public` / `member` / `admin` / `client` | 没带令牌 → 401 |
| **授权** | 你能干什么？ | **Rbac 权限点**（角色基线 ± 个人增减） | `forum.post.delete` → 403 |
| **业务规则** | 这个对象允不允许你动？ | 代码判断（**不是权限点**） | "只能删自己的帖子"、"锁定的帖子不能删" |

> ⚠️ **最容易犯的错：把"所有权"当权限点。**
> `forum.post.delete` 的语义是**"能删任意帖子"**（版主、管理员）；
> 而"能删**自己**的帖子"**不需要也不该**单独建一个权限点 ——
> 那是"登录了 + 这条是你的"，属于业务规则，写在服务层。
> 一旦给所有权建权限点，权限表会爆炸，而且每加一种资源都要加一条。

### 1.2 判定发生在三层（顺序固定）

```
① 守卫        auth:member / auth:admin      → 没过：401
② 账号状态    banned 拦登录；muted 拦写     → 没过：403（MEMBER_MUTED 之类）
③ 权限点      can:forum.post.delete         → 没过：403（SYS_FORBIDDEN）
④ 业务规则    所有权 / 状态 / 频率           → 没过：403 / 409（带业务错误码）
```

- ①②③ 适合放**路由中间件**（声明式、一眼能看出这个接口要什么权限）；
- ④ 只能放**服务层**（它跟你操作的是哪一条数据有关）。

### 1.3 前端那层不是安全边界

后台/官网按权限 key 控制按钮显隐，那只是**体验优化**。**后端必须独立判一遍。**
（这条写进铁律：`docs/standards.md` 第 0 节第 4 条里那个"没接库不算完成"是同一类要求。）

### 1.4 判定结果的缓存

`PermissionRegistry::effectiveFor()` 每次要查一次个人增减表。
接中间件时按 **user_id 做请求内缓存**（一次请求只算一次），不要每个中间件都算一遍。

## 2. 推进方式：每个模块一次做完（铁律 4）

后面每接一个模块，节奏固定这 6 步，**不许跳**：

| 步 | 做什么 | 产出 |
|---|---|---|
| 1 | 从 `docs/permissions.md` 圈出该模块的权限点 | 清单 |
| 2 | 列出该模块要做的接口，逐个标"需要哪个权限点" | **映射表**（写进模块文档） |
| 3 | 后端：路由挂 `can:<key>`（粗）+ 服务层判业务规则（细） | 代码 |
| 4 | 前端：按 key 控按钮显隐；**403 时给明确提示**（不能说"操作失败"） | 代码 |
| 5 | 测试：**每个权限点至少一对「有它 → 通过 / 没它 → 403」** | 测试 |
| 6 | 更新映射表 + CHANGELOG | 文档 |

> **第 5 步是唯一的保障。** 只写"有权限能通过"的测试，等于没测 ——
> 漏挂中间件的接口照样绿。**必须测"没有权限时被拒"**。

## 4. 建议的推进顺序（有依赖关系，别乱）

```
第 0 步  Rbac 收尾：can() + 鉴权中间件 + 按用户缓存
         ↑ 不做它，后面每个模块接权限都要返工
   ↓
第 1 步  02 Content（文章）
         ↑ 一期核心诉求"后台发文章 → 官网读到"；接口少、权限边界清晰、能当样板
   ↓
第 2 步  10 Blog → 11 Forum → 12 Feedback
         ↑ 都是"用户产内容"，权限模式几乎一样，可复用第 1 步的写法
   ↓
第 3 步  14 Product → 03 License → 04 Client
         ↑ 授权链（EA 那部分按你的要求延后）
   ↓
第 4 步  05 Audit / 17 Stats / 16 Plugin / 06 Crypto（密钥）
```

**每一步都按第 2 节那 6 步走完再开下一个** —— 这是你定的节奏，也是唯一能保证不出现
"接口做了但没拦"或者"前端假装拦了"的办法。

## 5. 何时该新增权限点

**加**：出现一类新的"能做的事"，且它不是"所有权"（见 1.1）。
**不加**：
- 所有权判断（"只能动自己的"）；
- 同一件事的更细粒度（`system.role` 已经够了，不必再拆 `system.role.create/edit/delete`）；
- 只是"某个接口需要登录"——那是守卫的事，不是权限点。

命名：`模块.动作`，全小写点分（后端与后台都有同一套正则校验）。

## 6. 第 0 步执行清单（Rbac 收尾：把"鉴权通道"建起来）

> 不先做这步，后面每个模块接权限都要返工。这里把要做的 5 件事定死。

### 6.0 三条硬要求（用户 2026-10-04 明确）

1. **权限只有一处主体**：权限挂在 **`users` 总表**上（`role_id` + `user_permissions`），
   管理员通过 `admins.user_id` 挂回总表。**不允许**出现"两处各算一半"。
2. **鉴权走同一个通道**：所有需要权限的接口**都过同一个中间件**，
   不允许在控制器里散落写 `if (! $user->can(...))`。
3. **没权限要给具体提示**：403 的 message 必须是
   **"你没有「删除帖子」权限"**（带上权限点的中文名），前端据此**弹窗**。
   只回"操作失败"之类的笼统话，等于把排查成本转给使用者。

### 6.1 任务清单

| # | 做什么 | 关键点 |
|---|---|---|
| 0.1 | **`admins` 加 `user_id`**（外键 → `users`），把 `root` 关联到一条总表记录并挂 `owner` 角色 | 不做这步，管理员在权限体系里是"没有角色的人"，一上 `can` 就整站 403 |
| 0.2 | **判定入口**：`PermissionRegistry::allows($subject, $ability)` | `$subject` 既可以是 `User`，也可以是 `Admin`（自动取其 `user`）；结果**按主体做请求内缓存**（一次请求只算一次） |
| 0.3 | **统一中间件** `permission:<key>` | 一个中间件管全部；未登录 401、无权限 403（带权限中文名） |
| 0.4 | **登录 / `me` 下发权限列表** | 只下发**自己那份**（不能指定"给我别人的"）；前端拿它控显隐 |
| 0.5 | **测试** | 每个权限点一对「有它 → 通过 / 没它 → **403**」；再加一条 **提权回归**：请求体里伪造 `role` / `permissions` → 照样 403 |

### 6.2 前端配套（属于第 0 步，不是"以后再说"）

1. **403 弹窗**：统一在 `api/client.ts` 那层拦，弹窗文案直接用后端 message；
2. **收到 403 后刷新一次权限列表**：否则被收走权限的人会一直看见"能点但一点就失败"的按钮；
3. **权限列表要能刷新**：登录时下发 + 手动/自动刷新两条路都要有。

### 6.3 提权防护（用户专门问过，这里定死）

| 风险 | 防护 |
|---|---|
| 改前端权限列表 | **无效** —— 服务端从不读客户端的权限声明，只认库里算的 |
| 请求体里塞 `role` / `permissions` | **无效** —— 服务端不读这些字段（有回归测试钉住） |
| 令牌被别人用了 | 属认证问题：令牌失效/登出即失效；后续可加"踢下线" |
| 权限被撤销后仍能操作 | 判定走预加载层 + 写操作 `flush()`，**下一个请求就生效** ✅ |

## 7. 本文档的维护方式

| 内容 | 谁维护 |
|---|---|
| 权限点清单、角色基线、矩阵 | **命令生成** —— 改完后台跑 `php artisan rbac:doc` |
| 模型（第 1 节）、推进方式（第 2 节）、顺序（第 4 节） | 手写，改动时同步 CHANGELOG |
| 各模块的"权限点 → 接口"映射表 | 写在各模块文档 `docs/modules/*.md` 里 |

> 提交前可跑 `php artisan rbac:doc --check` 自检权限文档有没有和数据库脱节。
