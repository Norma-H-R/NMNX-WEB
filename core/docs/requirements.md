# RBAC 设计结论（回答 D1 / R35 / R8 的权限问题）

## 两张表

| 表 | 是谁 | 登录入口 |
|---|---|---|
| `users` | 前台会员（客户）。注册即"普通用户" | `/api/v1/public` + `/api/v1/admin` 之外的会员入口 |
| `admins` | 后台管理者（我们运营方的人） | `/api/v1/admin/login` |

## 权限表**只有一套**，不是每个模块一张

这是回应"每个模块要对应一个表、综合起来查、数据库压力大"的顾虑：
**权限表全站共用一套**（标准 RBAC），通过**多态关联**同时挂在 `users` 和 `admins` 上，
业务模块只负责**声明自己有哪些权限名**，不负责建表。

```
roles                    角色：blog_author(博主) / forum_moderator(版主) / …
permissions              权限：post.create / post.publish / blog.manage / …
role_has_permissions     角色 → 权限
model_has_roles          谁 → 角色（model_type 多态：user 或 admin）
```

权限命名规范：`<模块>.<动作>`，例如 `post.create`、`post.publish`、`forum.moderate`。
新模块加权限 = 插几行 `permissions`，**不改表结构**。

## 三个身份落到哪

| 身份 | 怎么落 |
|---|---|
| 网站管理者 | 属于 `admins` 表；权限最全 |
| 博主 | `users` 用户持 `blog_author` 角色 |
| **帖主** | ⚠️ **不是角色**，是"这条帖子是谁发的"——属于**业务关系**（线程/帖子的 `author_id`），不要做成权限 |
| **版主** | `users` 用户持 `forum_moderator` 角色 **+ 单独一张 `board_moderators(board_id, user_id, level)`** 决定他管哪些版 |

**关键区分**（后面设计论坛时反复用到）：

- **RBAC 管"能不能做某类事"** → `can('forum.moderate')`
- **业务关联表管"对哪个对象做"** → `board_moderators` 决定管哪些版块

这样就不会出现"给每个版块建一个角色"导致角色爆炸。

## 性能：权限判断必须走缓存

权限是**每个请求都要判断**的东西，直接查 DB 才是真的压力大。做法：

1. 登录时把该主体的**权限名集合**算好，塞进 Redis：
   `nmnx:acl:{user|admin}:{id}` → `["post.create","post.publish",...]`
2. 请求时一次 `GET` 判断，不碰 DB
3. 角色/权限变更时**主动失效**该键
4. 权限很少变，缓存命中率极高

## C-7 的结论：一期只留接口，不实现算法（2026-10-03 确认）

不实现任何加密算法，只把**位置**留出来：

- 请求 / 响应结构里预留加密相关字段（`key_id`、`enc`、算法标识等）
- 代码里留出 `Encryptor` 抽象与注入点
- **算法怎么定、怎么协商，后期再实现**

> 理由（用户原话大意）：现在真正的复杂度**不在加密算法上**，而在"EA 初始化时那条请求的
> **接口形状**"上。字段一旦发出去，已经装在别人机器上的 EA 就改不动了 —— **字段要一次设计到位**。

原先担心的"EA 侧 MQL 没有 AES"这个问题因此**暂时不存在**：一期根本不要求 EA 做加解密。
等真要上整体加密时再评估（那时可能要走已有的 `mt5_dll`）。

## C-6 的结论：三类登录方式预留，一期只做邮箱 + 密码（2026-10-03 确认）

前台会员的登录方式定三类，**全部留接口、一期只落地邮箱 + 密码**：

| 方式 | 一期 | 说明 |
|---|---|---|
| 二维码登录（微信 / Telegram） | ⛔ 预留 | 接口后做 |
| 短信登录 | ⛔ 预留 | `users.phone` 列已预留 |

`MemberAuthService` 里留好（以后加 `loginByQr()` / `loginBySms()`，不改现有签名）。
